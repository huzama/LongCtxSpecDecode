Chapter 4 · Method and evaluation

Sparse self-speculation

Shared model weights. One hierarchical backbone KV cache. Sparse drafting and configurable verification.

Shared model, sparse execution

Long-context decoding pays for both model execution and attention over the KV cache. Highlight, introduced in Chapter 2, reduces attention access; projections and feed-forward layers still execute for every generated token. Self-speculation uses a cheaper pass of the same model to propose several tokens, then verifies them together.

The evaluated method combines Highlight selection with a shared coarse/refinement KV representation. Model weights and the Highlight indexer stay BF16. Drafting reads the coarse four-bit plane; verification reads both planes and uses either full attention or a selected context budget.

  1. Draft six tokensScore context on the first draft step. Reuse scores and update selection over six autoregressive steps, each with a 7% prompt-length budget.
  2. Verify togetherProcess the last emitted token and six proposals. Use full attention or a 50%, 40% or 25% verification budget; rewrite their KV.
  3. Accept and advanceCommit the matching greedy prefix. Emit a correction at rejection, or a bonus if all six proposals match.

Selection uses 16-token blocks. Blocks covering the last 64 tokens receive priority inside the budget. Direct Highlight refreshes scores every token; sparse verification computes fresh scores. The Highlight indexer is additional state, distinct from the shared backbone KV.

Sparse verification changes the target computation. Hierarchical verification approximates BF16 KV. Neither configuration carries an established lossless-output claim; numerical evidence and task quality are reported separately.

Cache representation and update

One backbone KV cache4-bit coarse + 4-bit refinementShared scales and minima · bounded BF16 recent/provisional buffer
Draft view7% selected history · coarse plane
Verifier viewFull / 50% / 40% / 25% history · both planes
  1. Stage: draft KV enters the BF16 provisional buffer.
  2. Rewrite: verification recomputes KV for the anchor and proposed positions in every layer.
  3. Commit: retain the verified accepted prefix and invalidate rejected positions. Process the emitted correction or bonus as the next input.
  4. Compress: encode older accepted groups into both packed planes. Recent and provisional entries remain BF16.

Keys use 128-token groups; values use 128-channel groups. Verification handles a compression boundary per query position while retaining all six proposals. Packed values are reconstructed into BF16 tiles for attention; the full context is never expanded into a second KV cache.

At eight KV heads, a 16-token page occupies 33,792 bytes including quantization metadata, or 51.56% of a BF16 page. Each request and layer also has a 263-position BF16 ring. This page ratio excludes the ring, indexer and scratch; measured peak memory includes the allocated cache pool.

The hierarchical representation follows QuantSpec. “4+4” denotes coarse plus refinement storage, not native FP8. Cache precision, model-weight precision and indexer precision are independent choices.

Throughput protocol

Common capacity
Calibrate all eight hierarchical methods, including graph storage, scratch, the full input, 512 output tokens and six lookahead slots. Use their largest common batch; native FP8 uses the identical batch and prompt cohort.
One batch per process
Each method runs one full batch in each of three fresh processes. No waiting requests, KV preemption, prefix caching or asynchronous scheduling. This is a matched-batch comparison, not each method’s independent peak capacity.
Decode window
Hold requests after their first output until every prefill is complete. Time until the first request finishes. Count emitted tokens after the first token; respect EOS. Exclude loading, compilation, capture, warm-up, prefill and the shrinking-batch tail.
Execution
Six draft graph replays and one verifier graph per steady round. Engine timing includes scheduling, input preparation, sampling and launch costs. Cap-shortened verification may use native eager execution; its exact query shape and elapsed time are audited.
Pairing
Repetitions 1/2/3 use physical B200-1 GPUs 2/3/0 across all methods. Each dispatch requires 60 seconds idle, no outside compute and a cooperative GPU lock.
Aggregation
Report the median of three process rates. Speedup divides unrounded medians by the matched full-context 4+4-bit AR rate. Acceptance pools uncensored counts; ranges describe process variation, not confidence intervals.
Audit
Verify frozen code, inputs and runtime; useful output counts and EOS; full-batch execution; graph traces; and cache transactions. Empty answers, generated thinking spans and post-EOS tokens fail validation. A lone leading closing-think delimiter is recorded without editing tokens or timing.

Completed scope: 2 models × 3 contexts × 9 methods × 3 processes = 162 timing runs, plus 48 capacity searches. The report contains no task-quality reruns for this final loader.

Hierarchical KV implementation

FA4 · packed 4+4-bit KV

FA4 performs attention, softmax and reduction. The packed loader supplies BF16 tiles from coarse or coarse-plus-refinement reads. Selection, cache transactions and graph execution are included in full-model throughput.

Each 16-token page stores both packed planes and shared quantization metadata. At eight KV heads this is 33,792 bytes, 51.56% of a BF16 backbone page. A separate bounded ring holds 263 BF16 positions per request and layer. This page ratio excludes that ring, the Highlight indexer and attention scratch.

FA4 hierarchical attention. Vectorized asynchronous packed reads, CUTLASS INT4 conversion and tile-local BF16 reconstruction feed FA4 tensor-core attention, softmax and reduction. No expanded context cache is allocated.

Address correction: full-capacity runs exposed 32-bit metadata-index overflow when a layer's cache exceeds 4 GiB. Physical page indices are now promoted to 64-bit before stride multiplication. The failure reproduces with the previous loader; all 17 corrected GPU checks passed, including large physical page addresses, sparse and dense reads, one- and seven-query attention, graph replay and cache transactions.

Both full-batch regressions passed: dense AR and full-context four-bit drafting at 4B / 32K / batch 42. All 27 subsequent timing runs also passed their saved-output and execution audits. Cache precision, selection and six-draft policy are unchanged. Current validation. Earlier attention-only timings remain in archived loader evidence; they are not timings of this correction.

How selector latency and memory are measured

Measurement protocol

Batch 1; six existing prompts per model/context; layers 2, 18 and 35. Three fresh processes per model/context and indexer format. Within each process, take the median of 18 capture medians per stage; each capture uses five warm-ups and 20 CUDA-graph samples of 20 calls. Initialization uses one call per sample. Loading, transfer, compilation, capture and warm-up are excluded.

Stage sum adds score, rank/index and gather medians within each process, then takes the median across processes. It can differ from the sum of separately displayed stage medians. It excludes initialization and is not a separately timed end-to-end latency. Highlight needs no KV gather; its missing gather contributes zero.

All 36 processes passed the saved per-capture checks. Original single-process observations are retained in the source evidence and are not pooled into these repetitions. Process medians, ranges and 720 source hashes.

Score includes acquisition and reduction. Vegas measures fused-attention time minus matched dense-attention time, plus reduction; paired samples retain negative measurement noise. Highlight uses native production kernels; Vegas uses our FP32 FA4 port; TriForce uses the PyTorch retrieval reference.

Extra KV is per-layer, batch-1 auxiliary storage: Highlight indexer keys (including MXFP4 scales), or gathered Vegas/TriForce KV. It excludes the shared full cache and scratch. Vegas collection buffers and TriForce chunk means each add about 8 / 16 / 31.88 MiB at the three lengths. These are identified buffers, not peak-memory measurements. The indexer-format column applies only to Highlight; all gathered backbone KV remains BF16.

Interpretation & limits

At matched budgets, MXFP4 changes Highlight’s stage sum by -25.8% to -3.9% relative to BF16. Its indexer cache uses 26.56% of BF16 storage including scales: 8.50 / 17.00 / 33.87 MiB versus 32.00 / 64.00 / 127.50 MiB. This is a 73.44% reduction in auxiliary indexer storage.

TriForce has the lowest score-stage time; ranking and gathering dominate its measured selection event. Highlight has the lowest summed stages in these implementations. Refresh frequency differs: Highlight scores once per draft round, Vegas refreshes after verification, and the released TriForce policy selects once at prefill then updates its tail. Tail-update latency is not measured. These event costs do not establish per-token speedups, complete system superiority, or selector latency at saturated batches.

Inputs use the main grid's checkpoints, prompts and YaRN settings with dense FA4. We replay seven queries from six greedy continuation tokens. Vegas uses both boundary queries; Highlight and TriForce use the last prefill query on the same prompt KV. Fixed-length captures may include EOS. They measure timing, not acceptance or task quality.

Selector-quality evidence comes from Chapter 2's attention-map and retrieval analysis (fig:distilled:attention-maps, fig:distilled:attention-retrieval). It supports the learned attention-approximation argument; these timing measurements do not establish equal selection quality against Vegas/TriForce at 7%, or equal quality between BF16 and MXFP4 indexers.

Proposal construction and acceptance

Each speculative round uses up to six guesses, one causal Jacobi update and one dense verification pass. Only verified predecessors enter history KV.

  • Random: uniform guesses from non-special vocabulary tokens.
  • Carry: unused, aligned predictions from the previous verification pass.
  • Prompt copying: match the longest 1–4-token suffix of accepted history in the original prompt; take the latest occurrence with a continuation and copy up to six following tokens. Carry and copying use random fallback.

Accepted/round counts emitted draft tokens. Emitted/round also counts verifier corrections or bonuses. Each speculative round uses two forward passes; prompt copying therefore emits about 2.2 tokens per forward.

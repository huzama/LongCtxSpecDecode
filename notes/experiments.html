01

Shared-model self-speculation

Highlight selects context for six autoregressive draft steps. Drafting and verification share BF16 model weights and one backbone KV cache; the Highlight indexer is additional state.

  1. Select & draftUse a 7% prompt-length attention budget. Score on the first draft step, then reuse scores while updating selection and provisional KV across all six steps.
  2. Verify jointlyProcess the last emitted token (the anchor) and six proposals with dense attention, or the configured sparse verification budget. Verification rewrites their KV.
  3. Accept & continueKeep the matching greedy prefix. Emit a correction on rejection or a bonus when all proposals match; continue from that emitted token.

Selection uses 16-token blocks. Blocks covering the last 64 tokens receive priority inside the budget. Budgets use the original prompt length; short CoT answer prompts can have too little budget for that window. Direct Highlight refreshes scores every token; sparse verification computes fresh scores.

Sparse verification changes attention and committed KV history; task quality and output agreement must be measured. Dense verification follows greedy prefix acceptance, with numerical limitations documented in validation.

Highlight is the selector developed in Chapter 2. This study evaluates its use in self-speculation and cache precision configurations; weight quantization and parallel drafting are separate studies.

02

One cache, two precision views

The BF16 cache is the reference configuration. Hierarchical storage adds coarse four-bit reads for drafting and combined 4+4-bit reads for verification.

Shared backbone KVCoarse 4-bit + refinement 4-bitShared scales and minima · BF16 recent / provisional buffer
Highlight draftSelected history · coarse view
Dense verifierFull history · combined view
  1. Stage: drafts write provisional KV into the bounded BF16 buffer.
  2. Rewrite: verification recomputes KV for the anchor and proposed positions at every layer. Historical KV stays in place.
  3. Commit or discard: retain verifier-computed KV for the accepted prefix and invalidate rejected positions. The correction or bonus is processed as the next input.
  4. Compress: older accepted groups are encoded from BF16 into both packed planes. Recent and provisional entries remain BF16.

Keys use 128-token groups; values use 128-channel groups. At a compression boundary, each verification query uses the view appropriate to its position. The older committed group can be encoded while its BF16 buffer values remain available. Rounds retain six drafts.

The combined view approximates eight-bit precision; it does not recover BF16 values. The hierarchy follows QuantSpec. The indexer, metadata, BF16 buffer and attention scratch all count toward memory. See measured cache results.

Validated implementation: the FA4 hierarchical backend passed packed-cache and transaction checks, plus full-model checks for 4B direct Highlight, 4B SV50 and 8B full-context four-bit drafting with dense verification. The corrected backend has audited 4B / 32K throughput measurements. Serial-output equivalence and hierarchical-cache / MXFP4 combinations remain unestablished. Validation scope.

Measurement protocol

Batch 1; the first six existing prompts per model/context; layers 2, 18 and 35. Each cell is the median of 18 capture medians. Each capture uses five warmups and 20 CUDA-graph samples of 20 calls. Sum of stages adds the score, rank/index and gather medians before rounding. It excludes initialization and is not an independently measured end-to-end latency. Highlight accesses selected pages without a KV gather; n/a gather therefore contributes zero to the sum.

Three fresh process repetitions per model/context and indexer format are being collected separately with the same inputs and settings. This report retains the original single-process measurements. Three-run medians and ranges will be added after the complete repetition grid passes audit.

Score includes acquisition and reduction. Vegas measures fused-attention time minus matched dense-attention time, plus reduction; paired samples retain negative measurement noise. Highlight uses native production kernels; Vegas uses our FP32 FA4 port; TriForce uses the PyTorch retrieval reference.

Extra KV is per-layer, batch-1 auxiliary storage: Highlight indexer keys (including MXFP4 scales), or gathered Vegas/TriForce KV. It excludes the shared full cache and scratch. Vegas collection buffers and TriForce chunk means each add about 8 / 16 / 31.88 MiB at the three lengths. These are identified buffers, not peak-memory measurements. Interpretation & limits

MXFP4 lowers Highlight's summed stages by 3.9–26.8% relative to BF16 at matched budgets, with the largest reduction at 130,560 tokens. Its indexer cache uses 26.56% of BF16 storage, including scales: 8.50 / 17.00 / 33.87 MiB rather than 32.00 / 64.00 / 127.50 MiB. This is a 73.44% reduction in indexer storage, not in total model or backbone KV memory.

TriForce has the lowest score-stage time; ranking and gathering dominate its measured selection event. Highlight has the lowest summed stages in these implementations. Refresh frequency differs: Highlight scores once per draft round, Vegas refreshes after verification, and the released TriForce policy selects once at prefill then updates its tail. Tail-update latency is not measured. These event costs do not establish per-token speedups, complete system superiority, or selector latency at saturated batches.

Inputs use the main grid's checkpoints, prompts and YaRN settings with dense FA4. We replay seven queries from six greedy continuation tokens. Vegas uses both boundary queries; Highlight and TriForce use the last prefill query on the same prompt KV. Fixed-length captures may include EOS. They measure timing, not acceptance or task quality.

Selector-quality evidence comes from Chapter 2's attention-map and retrieval analysis (fig:distilled:attention-maps, fig:distilled:attention-retrieval). It supports the learned attention-approximation argument; these timing measurements do not establish equal selection quality against Vegas/TriForce at 7%, or equal quality between BF16 and MXFP4 indexers.

03

Draft-weight scope

Only draft gate/up/down weights change from BF16 to INT4. Draft activations, attention, verifier weights and the shared backbone KV stay BF16. INT4 adds packed FFN weights, not a second backbone KV cache. Highlight uses BF16 indexer keys, a 7% budget and the last 64 tokens inside that budget. Scores refresh once per six-token draft round. Verification uses full attention.

QuantSpec’s released code informs the FFN-only weight scope; its hierarchical KV design is outside this experiment. MXFP4 indexer quantization is a separate component.

Initialization and acceptance definitions

Each speculative round uses up to six guesses, one causal Jacobi update and one dense verification pass. Only verified predecessors enter history KV.

  • Random: uniform guesses from non-special vocabulary tokens.
  • Carry: unused, aligned predictions from the previous verification pass.
  • Prompt copying: match the longest 1–4-token suffix of accepted history in the original prompt; take the latest occurrence with a continuation and copy up to six following tokens. Carry and copying use random fallback.

Accepted/round counts emitted draft tokens. Emitted/round also counts verifier corrections or bonuses. Each speculative round uses two forward passes; prompt copying therefore emits about 2.2 tokens per forward.

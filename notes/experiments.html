Chapter 4 · Method and evaluation

Sparse self-speculation

Shared model weights, one hierarchical backbone KV cache, sparse drafting and configurable verification.

Qwen3-4B / 8B · Six proposals · Greedy decoding

Method

The model drafts six tokens using Highlight-selected context and verifies them together. Drafting reads the coarse 4-bit KV plane at a 7% prompt-length budget; verification reads both planes (4+4 bits), using all context or 50%, 40% or 25%. Model weights and the indexer remain BF16, with one shared backbone KV cache.

  1. Draft

    Generate six proposals; score once and reuse scores within the round.

  2. Verify

    Check the anchor and six proposals together; recompute their KV.

  3. Accept

    Keep the matching prefix; emit a correction or bonus token.

Selection and verification details

Selection uses 16-token blocks. Budgets are fractions of the original prompt length, rounded down to whole blocks. Blocks covering the last 64 tokens receive priority inside the budget; priorities persist until fresh scoring. Direct Highlight refreshes scores every token. Sparse verification scores with the anchor query and shares one block table across all seven positions per layer and request, with causal masking. Its recency window ends at the final proposal. The Highlight indexer is additional state, distinct from the shared backbone KV.

Shared-selection sparse verification is not guaranteed to match per-token Highlight decoding. Hierarchical verification approximates BF16 KV. Neither configuration carries an established lossless-output claim; numerical evidence and task quality are reported separately.

  1. Stage: draft KV enters the BF16 provisional buffer.
  2. Rewrite: verification recomputes KV for the anchor and proposed positions in every layer.
  3. Commit: retain the verified accepted prefix and invalidate rejected positions. Process the emitted correction or bonus as the next input.
  4. Compress: encode older accepted groups into both packed planes. Recent and provisional entries remain BF16.

Compression advances through committed KV in 128-token groups. Keys use 128-token groups; values use 128-channel groups. At a boundary, verification retains the group's BF16 copy for earlier queries and uses its compressed representation for later queries, matching the sequential cache precision schedule. All six proposals remain in the round. Packed values are reconstructed into BF16 tiles for attention.

At eight KV heads, a 16-token page occupies 33,792 bytes including quantization metadata, or 51.56% of a BF16 page. Each request and layer also has a 263-position BF16 ring: two 128-token groups plus seven provisional positions. It holds recent committed KV, provisional KV and BF16 values retained across a compression boundary. Sparse attention reads only selected ring positions inside its block budget. This page ratio excludes the ring, indexer and scratch; measured peak memory includes the allocated cache pool.

The hierarchical representation follows QuantSpec. “4+4” denotes an unsigned coarse code and a signed residual, reconstructed as m + s·c + (s/16)·r. Coarse-only reads omit the residual codes but still load the shared scales and minima for accessed groups. These are not the upper and lower nibbles of conventional INT8, or native FP8. Cache precision, model-weight precision and indexer precision are independent choices.

What each comparison isolates

The AR baseline uses full attention, without proposals or verification. The full-context four-bit draft isolates KV precision; the two Highlight/full-verifier rows isolate coarse draft reads. SV50, SV40 and SV25 change only the verification attention budget within that comparison.

The full-context four-bit draft isolates KV precision; it is not a reproduction of QuantSpec’s quantized-weight configuration. Highlight uses learned selection rather than Vegas’s verification-derived scores.

Vegas and TriForce are compared for selector timing only. Chapter 2 supplies the attention-approximation analysis. These measurements do not establish equal selector quality or whole-system superiority over either method.

Throughput protocol

Common capacity
Calibrate all seven hierarchical methods, including graph storage, scratch, the full input, 512 output tokens and six lookahead slots. Use their largest common batch;
One batch per process
Each method runs one full batch in each of three fresh processes. No waiting requests, KV preemption, prefix caching or asynchronous scheduling. This is a matched-batch comparison, not each method’s independent peak capacity.
Decode window
Hold requests after their first output until every prefill is complete. Time until the first request finishes. Count emitted tokens after the first token; respect EOS. Exclude loading, compilation, capture, warm-up, prefill and the shrinking-batch tail.
Execution
Six draft graph replays and one verifier graph per steady round. Engine timing includes scheduling, input preparation, sampling and launch costs. Cap-shortened verification may use native eager execution; its exact query shape and elapsed time are audited.
Device pairing
Match the device assignment of each repetition across methods. Use an idle B200 for every process; individual process records retain device identity.
Aggregation
Report the median of three process rates. Speedup divides unrounded medians by the matched full-context 4+4-bit AR rate. Acceptance pools uncensored counts; ranges describe process variation, not confidence intervals.
Validity
Audit frozen inputs and runtime, EOS handling, useful output counts, full-batch execution and graph agreement. Reject post-EOS tokens, empty answers and generated thinking spans. Preserve any leading closing-think delimiter in both tokens and timing.
Attention calibration
Choose split counts offline using the same procedure for every method at the measured batch and query shape. Freeze those choices before timing.

Numerical scope

Graph/eager agreement and cache-transaction checks gate the main timing measurements. These checks validate execution, not equality to unquantized decoding. In the BF16-backbone output audit, dense verification agrees with dense AR through EOS in five of six settings. At 4B/130,560, 126/144 repeated appearances agree; the 18 differences involve one prompt from output token 70. Matched replay did not reproduce the mismatch. Sparse verification and MXFP4 have no dense-output equivalence guarantee.

INT4 packed/dequantized FFN relative L2 is below 0.001085; INT4/BF16 FFN relative L2 spans 0.0218–0.1392. These numerical checks alone do not establish generation quality or speed.

BF16-backbone comparison protocol
Inputs
Freeze the first 32 eligible Multi-LexSum validation cases before generation. Use nested document prefixes at 32,768 / 65,536 / 130,560 input tokens; static YaRN factors 2 / 3 / 4. Request a detailed 500–700-word summary. Greedy decoding, thinking off, seed 42; stop at configured EOS or 512 outputs, with no minimum.
Repetitions
Three fresh processes per cell. 4B/32K and 4B/64K use 32 sequential full batches per process; other settings use one full batch. Within each comparison, methods share the same dense denominator, prompt cohort and batch protocol.
Capacity
Common batches are bounded by measured BF16 SV50 / INT4 Highlight capacity, with 512 outputs and six lookahead slots reserved. Methods share the batch shown in each table; this is not an independent peak-capacity comparison.
Timing
Complete all dense prefills before timing. Hold requests after their first output until the whole batch is ready, then measure decode until the first request finishes. Exclude loading, initialization, compilation, warm-up, prefill, first tokens and the shrinking-batch tail. Include drafting, verification, sampling, scheduling and launch overhead. Use one CUDA graph per draft step. Async scheduling and prefix caching are off; no waiting requests or KV preemption are allowed during timed decode.
Acceptance
Useful tokens count emitted tokens, including the terminal round. Draft acceptance uses only nonterminal rounds with room for all six proposals plus correction/bonus; exclude and count terminal or cap-shortened rounds. Native counters before EOS clipping are diagnostic only.

How selector latency and memory are measured

Measurement protocol

Batch 1; six frozen prompts per model/context; layers 2, 18 and 35. Three fresh processes per model/context and indexer format. Within each process, take the median of 18 capture medians per stage; each capture uses five warm-ups and 20 CUDA-graph samples of 20 calls. Initialization uses one call per sample. Loading, transfer, compilation, capture and warm-up are excluded.

Stage sum adds score, rank/index and gather medians within each process, then takes the median across processes. It can differ from the sum of separately displayed stage medians. It excludes initialization and is not a separately timed end-to-end latency. Highlight needs no KV gather; its missing gather contributes zero.

Per-capture numerical and selection checks cover both budget protocols. Process medians, ranges and source hashes.

Score includes acquisition and reduction. Vegas measures fused-attention time minus matched dense-attention time, plus reduction; paired samples retain negative measurement noise. Highlight uses fused kernels; Vegas uses our FP32 FA4 port; TriForce uses the PyTorch retrieval reference.

Extra KV is per-layer, batch-1 auxiliary storage: Highlight indexer keys (including MXFP4 scales), or gathered Vegas/TriForce KV. It excludes the shared full cache and scratch. Vegas collection buffers and TriForce chunk means each add about 8 / 16 / 31.88 MiB at the three lengths. These are identified buffers, not peak-memory measurements. The indexer-format column applies only to Highlight; all gathered backbone KV remains BF16.

Interpretation & limits

At matched budgets, MXFP4 changes Highlight’s stage sum by -25.8% to -3.9% relative to BF16. Its indexer cache uses 26.56% of BF16 storage including scales: 8.50 / 17.00 / 33.87 MiB versus 32.00 / 64.00 / 127.50 MiB. This is a 73.44% reduction in auxiliary indexer storage.

TriForce has the lowest score-stage time; ranking and gathering dominate its measured selection event. Highlight has the lowest summed stages in these implementations. Refresh frequency differs: Highlight scores once per draft round, Vegas refreshes after verification, and the released TriForce policy selects once at prefill then updates its tail. Tail-update latency is not measured. These event costs do not establish per-token speedups, complete system superiority, or selector latency at saturated batches.

Inputs use the BF16-backbone checkpoints, prompts and YaRN settings with dense FA4. We replay seven queries from six greedy continuation tokens. Vegas uses both boundary queries; Highlight and TriForce use the last prefill query on the same prompt KV. Fixed-length captures may include EOS. They measure timing, not acceptance or task quality.

Selector-quality evidence comes from Chapter 2's attention-map and retrieval analysis (fig:distilled:attention-maps, fig:distilled:attention-retrieval). It supports the learned attention-approximation argument; these timing measurements do not establish equal selection quality against Vegas/TriForce at 7%, or equal quality between BF16 and MXFP4 indexers.

Attention agreement measures selector approximation on fixed queries; it does not establish generation quality.

The attention diagnostic uses six frozen 32,768-token prompts per model at layers 2, 18 and 35: 18 captures per model. Each capture uses the last prefill query, dense FA4 and static YaRN factor 2. The native oracle maximizes retained attention mass using the same shared 16-token blocks, budget and 64-token recency rule. Boundaries of the evidence
  • Quality: retrieval and a 60-question LongBench subset do not establish general quality preservation. Sparse verification changes the target computation; quantization can also change selection and generated outputs.
  • Speed and quality: scored tasks have no matched timing. Their scores and the fixed-output throughput results are separate evidence, not measured points on a speed–quality curve.
  • Capacity: throughput compares fixed batches selected for BF16 capacity. It does not measure the maximum throughput or batch capacity enabled by MXFP4.
  • Selector comparison: batch-1 event timing uses different refresh policies and implementation paths. It does not measure complete Vegas/TriForce systems, equal-quality selection, or amortized cost per generated token.
  • Repeatability: current throughput and selector timings each have three fresh process repetitions. Selector ranges describe process variation, not confidence intervals. Earlier cross-host throughput controls retain their original pairing limitations.

Projection scope, timing and provenance

Same 8B / 32K / batch-25 workload, one instrumented process per variant and 81 full-batch rounds each. Both use four-bit Highlight KV reads and a BF16-weight verifier with dense 4+4-bit KV reads. The INT4 variant quantizes all 252 decoder projections: Q, K, V, attention output and the three FFN projections in each layer. Activations, embeddings, norms, LM head and indexer remain BF16.

Stage times are means; throughput uses the all-prefills-complete to first-request-finish window. INT4 increases draft time by 20.81% and lowers throughput by 8.96%. Marlin W4A16 uses asymmetric groups of 128; packed draft weights add 3.36 GiB. All 25 outputs reach the cap without post-EOS tokens. This single-process diagnostic does not establish task-quality equivalence. Stage measurements · Numerical audit and provenance.

The cache representation and update policy are defined in Method & Setup; cache-only ablations appear in Main Results.

FFN quantization scope

Only draft gate/up/down weights change from BF16 to INT4. Draft activations, attention, verifier weights and the shared backbone KV stay BF16. INT4 adds packed FFN weights, not a second backbone KV cache. Highlight uses BF16 indexer keys, a 7% budget and the last 64 tokens inside that budget. Scores refresh once per six-token draft round. Verification uses full attention.

QuantSpec’s released code informs the FFN-only weight scope; its hierarchical KV design is outside this experiment. MXFP4 indexer quantization is a separate component.

Fixed-prefix agreement diagnostic

Six 32K short-answer prompts produce only six pre-EOS prefix states. All four draft variants match 36/36 teacher-forced predictions and accept all six freely drafted tokens at those states. This sample cannot distinguish their drafting quality.

The full diagnostic includes 48 prefix states, of which 42 follow EOS. Those states and forced-continuation timing are excluded from the generation-performance comparisons. Agreement counts next-token matches; acceptance counts the matching draft prefix and excludes correction or bonus tokens. Proposal construction and acceptance

Each speculative round uses up to six guesses, one causal Jacobi update and one dense verification pass. Only verified predecessors enter history KV.

  • Random: uniform guesses from non-special vocabulary tokens.
  • Carry: unused, aligned predictions from the previous verification pass.
  • Prompt copying: match the longest 1–4-token suffix of accepted history in the original prompt; take the latest occurrence with a continuation and copy up to six following tokens. Carry and copying use random fallback.

Accepted/round counts emitted draft tokens. Emitted/round also counts verifier corrections or bonuses. Each speculative round uses two forward passes; prompt copying therefore emits about 2.2 tokens per forward.
